예매 사이트의 취소표가 풀리는 순간을 알림으로 받고 싶었다.
도구를 거의 다 만들어 놓고, 마지막에 대상 사이트를 열어 보고서 프로젝트를 접었다.
**잔여석이 가상 대기열 뒤에 있었다.**

접은 것 자체보다, 그 사실을 **마지막에** 알게 된 과정이 기록할 만하다.

## 시작할 때 정한 범위

먼저 "하지 않을 것"부터 못 박았다.

- 자동 좌석 선점 / 자동 예매 / 자동 결제
- 캡차·봇 탐지 우회, User-Agent 위조, 프록시 IP 로테이션
- 로그인 자동화, 계정 정보 저장

남은 범위는 **감지와 알림까지**다. 좌석이 풀린 사실을 빠르게 알려주고 예매창을 열어 주는 것으로 끝내고, 좌석 선택과 결제는 사람이 한다.

이 제약이 기술 선택을 결정했다. 대상 사이트는 로그인해야 잔여석이 보이는데, 별도 서버나 독립 실행 프로그램으로 만들면 **세션 쿠키를 복제해서 들고 있어야 한다.** 반면 Chrome 확장으로 만들면 사용자가 이미 로그인한 세션을 브라우저가 알아서 붙여 준다. 쿠키를 읽거나 저장하는 코드가 아예 필요 없어진다.

> "하지 않을 것"을 먼저 정하면 아키텍처가 따라온다. 이건 제약이 아니라 설계 입력이다.

## 순서를 잘못 잡았다

계획서에는 이렇게 적었다.

> 1단계: 잔여석을 어떤 요청으로 가져오는지 특정한다. **코드 작성 전에 반드시 선행한다.**

그래 놓고 1단계를 건너뛰었다. 이유는 그럴듯했다. 조사는 로그인 세션이 필요해서 사람 손을 타야 하고, 나머지 모듈 중 상당수는 **사이트 응답 형태와 무관한 순수 로직**이다. 기다릴 이유가 없어 보였다.

그래서 먼저 만든 것들:

| 모듈 | 내용 |
| --- | --- |
| 조회 주기 계산 | 기본 간격에 랜덤 지터, 실패 시 지수 백오프 |
| 저장소 래퍼 | 감시 대상·설정·스냅샷·변화 이력·요청 카운터 |
| 감지 로직 | 잔여석 0 → 1 이상 전이 판정, 알림 쿨다운 |
| 즐겨찾기·단축키 | 예매창 빠른 진입 |

테스트 109건까지 갔다. 판단 자체는 틀리지 않았다. 저 모듈들은 지금도 멀쩡히 살아 있다.
틀린 건 **순서**였다.

## 조사에서 드러난 것

마침내 브라우저로 대상 URL을 열었다. 세 가지가 한꺼번에 나왔다.

### 1. URL이 이미 죽어 있었다

상품 페이지 주소로 들어가면 대기열 도메인을 거쳐 **사이트 메인**으로 튕겨 나왔다. 상품 페이지가 아니다. 같은 경로를 새 도메인에서 열면 404였다.

사이트가 통째로 다른 커머스 플랫폼으로 이전한 뒤였다. 프로젝트 전체가 이미 존재하지 않는 주소를 전제로 설계돼 있었던 셈이다.

### 2. 안내 페이지에는 잔여석이 없었다

새 구조에서 예매 안내 페이지를 열고 발생한 요청 67개를 전부 확인했다. **회차나 잔여석을 담은 요청은 하나도 없었다.** 서버 렌더링 HTML인데 그 HTML 안에도 없었다.

대신 페이지에 이런 문구가 있었다.

> 더 보기 클릭 시 예매전용 플랫폼으로 이동합니다.

안내문과 실제 예매가 분리된 구조였다.

### 3. 예매 구간 전체가 가상 대기열 뒤에 있었다

페이지 소스에 대기열 솔루션의 SDK가 붙어 있었다.

```html
<script data-xq-server="..." data-xq-usepopup="true"
        src="/js/xqueue-adapter.v1.min.js"></script>
```

이게 결정타였다.

## 가상 대기열이 있다는 건 무슨 뜻인가

가상 대기열(virtual waiting room)은 오픈 시각에 몰리는 트래픽을 **직렬화**하는 장치다. 사용자를 큐에 세우고 순번대로 통과시켜, 뒤쪽 시스템이 받는 동시 요청 수를 일정하게 유지한다.

중요한 건 부수 효과다. 대기열은 **자동화된 반복 접근을 막는 역할도 한다.** 한 번 통과한 세션에만 접근을 허용하므로, 짧은 주기로 반복 조회하려면 매번 큐를 통과하거나 큐를 건너뛰어야 한다.

즉 폴링 기반 감시와 가상 대기열은 **구조적으로 양립하지 않는다.** 둘 중 하나를 포기해야 한다.

- 대기열을 통과해서 폴링한다 → 4초마다 큐에 진입 시도. 현실적이지 않고 계정 차단 위험이 크다.
- 대기열을 건너뛴다 → 봇 차단 장치 무력화. 처음에 "하지 않을 것"에 적어 둔 바로 그 영역이다.

세 번째 선택지는 없었다. 그래서 접었다.

## 범위 제외 목록이 중단 지점을 미리 정해 준다

여기서 의외의 수확이 있었다.

프로젝트 시작할 때 적은 "하지 않을 것" 목록은 그때는 그냥 윤리적 선언처럼 보였다. 그런데 막상 벽에 부딪히니 **판단 기준으로 작동했다.** "대기열을 우회하면 가능한가?"라는 질문이 나왔을 때, 고민할 필요 없이 그 줄을 다시 읽고 끝냈다.

이 목록이 없었다면 "조금만 우회하면 되는데"를 며칠 더 붙들고 있었을 가능성이 높다.

> 무엇을 안 할지 먼저 적어 두면, 그만둘 지점이 미리 정해진다.

## 남은 것

버린 건 **사이트 어댑터 하나**다. 대기열과 무관한 나머지는 전부 살아남았다.

- 조회 주기 계산, 저장소 래퍼, 감지 로직 — 감시 대상이 "잔여석"에서 무엇으로 바뀌든 구조가 같다
- 즐겨찾기 + 단축키 — 사이트를 가리지 않는다. 이 기능만 떼어내도 쓸모가 있다

어댑터를 모듈 경계로 분리해 둔 덕이다. 호스트명에서 어댑터를 찾고, 어댑터가 사이트 응답을 공통 형태로 바꿔서 올리는 구조였다. 사이트가 통째로 사라져도 영향 범위가 파일 하나로 끝났다.

## 정리

세 가지가 남았다.

**전제 검증은 비용이 아니라 설계의 일부다.** "코드 작성 전에 반드시 선행한다"고 적어 놓고 건너뛴 대가가 이번 경우다. 다행히 재작업이 어댑터 하나로 끝났지만, 레이어를 덜 나눴다면 전부 버렸을 것이다.

**사람 손을 타는 단계를 뒤로 미루면 위험이 커진다.** 미룬 이유가 "협조가 필요해서"였는데, 협조가 필요한 단계일수록 전체 전제를 뒤집을 정보를 들고 있는 경우가 많다.

**외부 시스템을 전제로 한 프로젝트는 그 시스템이 변한다는 걸 기본값으로 깔아야 한다.** 이번엔 도메인 이전, 플랫폼 교체, 대기열 도입이 전부 내가 모르는 사이에 일어나 있었다.
