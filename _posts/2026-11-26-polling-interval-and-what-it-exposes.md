굿즈 도감에 "지금 살 수 있는지"를 띄우고 있었다. 수집은 하루 한 번이었다.

같은 공식몰을 **3분마다** 보는 사이트가 있는 걸 알게 되면서 주기를 들여다봤는데,
정작 배운 것은 주기 그 자체가 아니었다.
주기를 줄이는 순간 그 전까지 숨어 있던 것들이 차례로 드러났다.

## 1. 주기를 줄이는 비용은 요청량이 아니라 런타임에 있다

먼저 "3분이 어떻게 가능한가"를 봤다. 응답 헤더 한 줄이 답이었다.

```
Server: nginx/1.24.0 (Ubuntu)
```

서버리스가 아니라 **자기 서버**다. 그러면 프로세스가 계속 떠 있고,
`setInterval(3분)` 한 줄로 끝난다. 직전 스냅샷도 메모리에 그대로 있다.

이쪽은 GitHub Actions다. 모델이 다르다.

| | 상주 프로세스 | 매번 새 러너 |
| --- | --- | --- |
| 실행 준비 | 없음 | checkout + 의존성 설치 **30~50초** |
| 최소 주기 | 제한 없음 | cron **5분**, 지연 흔함 |
| 직전 상태 | 메모리에 있음 | DB에서 다시 읽어야 |

Actions는 "매번 새 컴퓨터를 빌려 켜는" 모델이다. 준비 시간이 주기의 1/4을 먹는
구조에서는 3분이 성립하지 않는다.

지연도 말로만 듣던 게 아니었다. 같은 날 예약 실행 하나가 이렇게 떴다.

```
cron        '0 18 * * *'  = 18:00 UTC
실제 실행    01:55 UTC                  ← 약 8시간 늦게
```

### 요청량은 생각보다 문제가 아니었다

처음엔 "3분마다 전량을 받으면 남의 상용몰에 하루 2만 요청"이라고 계산했다.
숫자는 맞지만 무게를 잘못 읽은 것이었다. 압축을 안 셌다.

```
카탈로그 1페이지   압축 없이 793KB → br/gzip 69KB   (8.7%)
전량 43페이지      약 3~4MB
```

JSON은 반복되는 키 덕에 10배 가까이 줄어든다.
3분마다 받아도 하루 2GB, 분당 14요청(초당 0.24회)이다.
VPS 전송량으로는 거스름돈이고, 크롤러 속도로도 예의 바른 편이다.

**막는 것은 대역폭이 아니라 스케줄러와 콜드 스타트였다.**

### 작업량을 반으로 줄인 관찰

전량 수집은 로케일을 둘 받는다. 한국어 상품명과 일본어 상품명을 같이 담아야 해서다.
그래서 한 바퀴가 86요청이 된다.

그런데 **재고는 로케일과 무관하다.** 한 로케일로만 돌면 43요청으로 끝난다.
이름을 다시 받을 이유가 없으니 절반이 그대로 빠진다.

```
전량 수집   ko+ja  86요청  — 하루 1회
재고 스윕   ko     43요청  — 30분마다
```

"다시 받아야 하는 것"과 "안 바뀌는 것"을 가르면 주기를 다르게 줄 수 있다.
이것이 하루를 30분으로 줄인 전부다.

### 싼 길을 찾다가 막힌 곳

전량을 받지 않고 "무엇이 바뀌었나"만 알 수 있으면 더 싸진다.
Shopify 스토어의 사이트맵에는 상품마다 `lastmod`가 붙어 있어서 그걸 노렸다.

재 보니 쓸 수 없었다.

```
sitemap_products_11.xml   619건
서로 다른 lastmod 값       1개
그 값                      내가 요청한 바로 그 시각
```

619건 전부 같은 시각, 그것도 **요청하는 순간**이 찍힌다.
요청 시점에 만들어 주는 값이라 변경 신호가 아니다.

사이트맵 `lastmod`를 증분 수집의 기준으로 삼기 전에 분포를 한 번 찍어 봐야 한다는 교훈.

## 2. 간헐적 실패는 배치 크기로 막을 수 없다

주기를 줄이기로 하고 나서, 바로 그날 기존 적재가 죽었다.

```
[스토어A] 10,616건 — 22배치
  14/22 — 500건 적재
  15번째 배치 실패: canceling statement due to statement timeout
```

한 배치가 삐끗했는데 나머지 8배치가 통째로 날아갔다.

반사적으로 "배치를 줄이자"는 생각이 들었는데, 재 보니 틀린 처방이었다.

| 배치 | 배치 수 | 중간 | 최대 | 합계 |
| --- | --- | --- | --- | --- |
| 250 | 43 | 922ms | 5,430ms | 47.2초 |
| 500 | 22 | 1,222ms | 6,645ms | 40.2초 |
| 1000 | 11 | 1,928ms | 3,997ms | 25.6초 |

**같은 일인데 474ms에서 6,645ms까지 14배 흔들린다.**
배치마다 하는 일이 똑같고, 관련 표는 전부 1~2만 행이며 인덱스도 다 걸려 있다.
질의 계획 문제가 아니라 **공유 인스턴스의 CPU·IO 지터**다.

두 점으로 선형 모델을 맞추면 이렇게 나온다.

```
t(250)  = a +  250b =  922ms
t(1000) = a + 1000b = 1928ms
→ b ≈ 1.3ms/행,  a ≈ 590ms

검산: t(500) ≈ 590 + 670 = 1,260ms   (실측 1,222ms)
```

호출당 고정비가 590ms다. 그래서 배치를 절반으로 줄이면 왕복이 두 배가 되어
**합계가 오히려 늘고**(40.2 → 47.2초), 최대값은 거의 그대로다.

### 고칠 것은 재시도가 없다는 쪽이었다

지터로 생기는 간헐적 실패는 크기로 못 막는다. 다시 보내면 된다.

재시도해도 되는 근거는 **멱등성**이다.
적재 함수가 키 기준 upsert이거나 단순 UPDATE라면, 같은 배치를 두 번 보내도 결과가 같다.
타임아웃으로 취소된 트랜잭션은 데이터베이스가 롤백을 보장한다.
이 두 가지가 성립하지 않으면 재시도는 위험한 선택이 된다.

에러 종류를 가릴지도 고민했는데, 가리지 않기로 했다.

- 일시적인 것을 영구적인 것으로 잘못 보면 → 적재가 통째로 날아간다
- 영구적인 것을 일시적인 것으로 잘못 보면 → 몇 초 늦게 같은 에러를 받는다

손해가 한쪽으로 크게 기울어 있다. 타임아웃만 백오프를 3배로 둔다.
인스턴스가 숨이 찬 상태인데 바로 다시 보내면 같은 자리에서 또 죽는다.

```js
// 재시도 직전에 알린다. 조용히 넘어가면 DB가 느려지는 것을 모르고 지나간다
const waitMs = isStatementTimeout(message) ? backoff * 3 : backoff;
onRetry({ attempt, waitMs, message });
await sleep(waitMs);
backoff *= 2;
```

마지막 줄이 제일 중요하다. **재시도를 넣으면 실패가 로그에서 사라진다.**
그래서 재시도할 때마다 반드시 찍게 했다. 재시도 줄이 늘어나는 것 자체가
"DB가 느려지고 있다"는 신호여야 한다.

## 3. 시각을 화면에 올리는 순간 드러난 것

재고를 30분마다 받게 됐으니, 그 값이 언제 것인지 화면에 밝히기로 했다.
붙이려고 보니 기존 표기에 두 가지 문제가 있었다.

### 렌더하는 쪽이 시간대를 정한다

```js
// 이 값은 "코드가 도는 기계"의 시간대를 따른다
`${date.getMonth() + 1}/${date.getDate()} ${date.getHours()}시`
```

서버리스 런타임은 보통 UTC로 돈다. 그래서 서버가 렌더한 HTML에는 이렇게 박혔다.

```
서버가 내려준 글자   11/25 7시에 확인한 재고예요
브라우저가 다시 그림  11/25 16시에 확인한 재고예요
```

**9시간이 튄다.** 그때까지는 이 문구가 hover tooltip 안에만 있어서 눈에 띄지 않았다.
화면에 올리는 순간 첫 페인트에서 바로 보이게 된다.

고치는 방향은 "브라우저 시간대를 따르게" 가 아니라 **"양쪽이 같은 글자를 내게"** 다.
표시 시간대를 하나로 못박는다.

```js
const FORMAT = new Intl.DateTimeFormat('en-US', {
  timeZone: 'Asia/Seoul',
  month: 'numeric',
  day: 'numeric',
  hour: '2-digit',
  minute: '2-digit',
  hourCycle: 'h23',   // 두지 않으면 엔진에 따라 자정이 24:00
});
```

이 테스트는 **개발 기계가 한국 시간대면 틀린 코드도 통과한다.**
배포 환경과 어긋난 지점이 정확히 거기였다. 그래서 두 조건으로 돌린다.

```bash
npm test          # 기계 시간대 그대로
TZ=UTC npm test   # 배포 환경과 같은 조건
```

예전 구현을 두 시간대에서 돌려 보면 테스트에 이가 있는지 바로 안다.

```
TZ=UTC         2026-11-25T07:13:59Z → 11/25 7시
TZ=Asia/Seoul  2026-11-25T07:13:59Z → 11/25 16시
```

### 표기 해상도가 갱신 주기를 따라가야 한다

하루에 한 번 받을 때는 `11/25 16시`로 충분했다.
30분마다 받으면 16:13과 16:43이 똑같은 글자가 된다.

**주기를 줄인 의미가 표기에서 사라진다.** 분까지 적어야 했다.

### 상대 시간을 쓰지 않은 이유

"7분 전"이 더 읽기 좋다. 그런데 이 페이지는 ISR로 5분 캐시된다.
서버가 그려 둔 "방금"이 이미 5분 묵은 글자일 수 있다.

절대 시각은 그런 거짓말을 하지 않는다. 캐시된 페이지에서도 `16:13`은 여전히 16:13이다.
상대 시간을 쓰려면 마운트 이후에 클라이언트에서 계산해야 하는데,
그러면 첫 페인트에서 글자가 한 번 바뀐다. 그 깜빡임을 사기에는 얻는 게 적었다.

## 결과

```
재고가 묵는 창    24시간 → 30분
재고 스윕         45요청 · 89초 (적재까지 전체 2분 36초)
적재             6배치 · 약 10초
```

화면에는 이렇게 나온다.

```
재고 11/25 16:13 기준
```

배포된 HTML을 직접 열어 서버가 내려주는 글자가 KST인지 확인했다.
예전 UTC 형식은 0건. 서버가 이미 맞게 그려 주므로 브라우저가 고쳐 쓸 것이 없다.

## 정리

세 가지가 같은 줄에 있었다.

1. **폴링 주기는 대역폭이 아니라 런타임이 정한다.** 상주 프로세스가 없으면
   스케줄러 최소 간격과 콜드 스타트가 하한선을 그린다. 그리고 "다시 받아야 하는 것"과
   "안 바뀌는 것"을 가르면 같은 예산으로 주기를 줄일 수 있다.

2. **간헐적 실패는 크기가 아니라 멱등성으로 다룬다.** 고정비가 큰 호출에서 배치를
   줄이면 총시간이 늘고 스파이크는 남는다. 다시 보내도 결과가 같은지가 기준이고,
   재시도를 넣는 순간 로그에 흔적을 남기는 것이 함께 와야 한다.

3. **주기를 줄이면 표기가 따라와야 한다.** 해상도(시 → 분)도, 시간대도.
   시간대는 "어느 기계가 렌더하는가"가 정하므로, 서버와 브라우저가 같은 글자를 내도록
   표시 시간대를 못박는 것이 맞다.

가장 크게 남은 것은 **처음 세운 처방 두 개가 다 틀렸다는 것**이다.
"하루 2만 요청은 부담이 크다"도, "배치를 줄이면 타임아웃이 준다"도 측정하니 반대였다.
둘 다 그럴듯했고, 둘 다 몇 분이면 재 볼 수 있는 것이었다.
