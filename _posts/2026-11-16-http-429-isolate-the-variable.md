## 문제 상황

공개된 상품 데이터를 받아오는 수집 스크립트가 처음부터 끝까지 `429 Too Many Requests` 로 막혔다.

```
HTTP 429 https://example-store.test/products/1234.json
```

재시도와 지수 백오프를 넣어도 똑같았다. 요청 간격을 1초에서 3초로 늘려도 마찬가지였다.
그런데 **같은 URL을 터미널에서 수동으로 한 번 호출하면 200이 돌아왔다.**

같은 주소, 같은 헤더인데 스크립트로 보내면 429, 손으로 보내면 200. 여기서 시작했다.

## 걷어낸 가설들

진단을 세 번 틀렸다. 틀린 과정 자체가 이 글의 요지라서 그대로 적는다.

### 가설 1 - 실행 환경이 네트워크를 제한한다

스크립트만 막히니 실행 환경 탓이라고 생각했다.
같은 환경에서 다른 호스트로 요청해 보니 멀쩡히 200이 왔다. 기각.

### 가설 2 - IP 단위 rate limit에 걸렸다

가장 그럴듯했다. 하지만 이 가설이 맞다면 **수동 요청도 같이 막혀야 한다.**
수동 요청은 계속 200이었다. 기각.

### 가설 3 - User-Agent로 봇을 거른다

스크립트는 식별용 커스텀 User-Agent를 보내고 있었다.
이것도 나중에 반증됐는데, 순서상 한참 뒤였다.

## 결정적 단서는 "부분적으로 성공"하는 지점이었다

전송 수단을 `curl` 로 바꿔 보니 **일부는 통과했다.**

```
스토어 통화: JPY        <- /meta.json 조회 성공
Error: HTTP 429 ...     <- 목록 조회 실패
```

가벼운 엔드포인트(`/meta.json`)는 200인데 목록 조회만 429.
**전송 수단이 통째로 차단된 거라면 둘 다 막혀야 한다.** 둘이 갈린다는 건 차단 기준이 전송 수단 하나가 아니라는 뜻이다.

여기서 "뭔가 막혔다"가 "무엇이 다를 때 갈리는가"로 질문이 바뀌었다.

## 원인 1 - 요청 수 자체가 과했다

먼저 설계를 다시 봤다. 상품을 **하나씩** 상세 조회하도록 짜 놨었다.

```
상품 9,000여 건 × 로케일 2개 = 18,000회가 넘는 요청
```

상대 입장에서 보면 그냥 과한 트래픽이다. 429가 나는 게 당연했다.

그런데 같은 서비스의 컬렉션 목록 경로에 페이지 파라미터가 있었다. 한 번에 250건씩 받을 수 있다.

```
GET /collections/all/products.json?limit=250&page=1
```

응답에 들어 있는 필드는 개별 조회와 동일했다. 바꾸고 나니 **18,000여 회가 37회**로 줄었다.

차단 여부와 무관하게 이게 맞는 설계였다. 애초에 1만 8천 번 두드릴 일이 아니었다.

## 원인 2 - 전송 클라이언트 빌드에 따라 갈렸다

요청 수를 줄이고도 여전히 간헐적으로 429가 났다. 여기서 변수를 하나씩 고정했다.

같은 URL에 **User-Agent만** 바꿔 비교했다.

```bash
# 기본 UA
curl -s -o /dev/null -w "%{http_code}\n" --compressed "$URL"
# 커스텀 UA
curl -s -o /dev/null -w "%{http_code}\n" --compressed -A "my-collector/0.1" "$URL"
```

둘 다 200이었다. **가설 3(User-Agent) 기각.** 위장해서 통과한 게 아니라 애초에 숨길 게 없었다.

그렇다면 남은 변수는 하나였다. 어떤 `curl` 실행 파일이 잡히느냐.

| 클라이언트 | 가벼운 엔드포인트 | 목록 조회 |
| --- | --- | --- |
| Node 내장 fetch | 429 | 429 |
| curl 8.22.0 (Windows 기본) | 200 | 429 |
| curl 8.7.1 (Git 번들) | 200 | **200** |

Windows에는 `curl` 이 두 개 있다. 그리고 **어느 쪽이 잡히는지는 실행한 셸에 따라 다르다.**

```
PowerShell / cmd  ->  C:\Windows\System32\curl.exe
Git Bash          ->  C:\Program Files\Git\mingw64\bin\curl.exe
```

Node의 `child_process` 는 셸을 거치지 않고 `PATH` 에서 실행 파일을 찾는다.
그래서 **같은 스크립트라도 어느 셸에서 실행했느냐에 따라 전혀 다른 바이너리가 요청을 보낸다.**

스크립트를 PowerShell에서 돌리면 429, Git Bash에서 돌리면 200. 코드는 한 글자도 다르지 않다.

## 해결 방법

### 1. 요청 수를 줄인다 (효과가 가장 컸다)

목록 일괄 조회로 바꿔 요청 수를 500분의 1로 줄였다.

### 2. 전송에 쓰는 실행 파일을 고정할 수 있게 한다

```ts
// PATH 의 curl 을 기본으로 쓰되, 필요하면 경로를 지정할 수 있게 둔다
const CURL_PATH = process.env.COLLECT_CURL_PATH ?? 'curl';
```

### 3. 429가 나면 "지금 무엇으로 보내고 있는지"를 같이 출력한다

원인을 짐작하기 어려운 에러라, 에러 메시지 자체에 단서를 넣었다.

```ts
function explain429(): void {
  console.error([
    '목록 조회가 429(요청 과다)로 막혔습니다.',
    `현재 전송에 쓰는 curl: ${getCurlVersion() ?? '확인 실패'}`,
    '가벼운 엔드포인트는 통과하는데 목록만 막힌다면 클라이언트 빌드 차이일 수 있습니다.',
    '다른 셸에서 실행해 보세요(PATH 의 curl 이 달라집니다).',
  ].join('\n'));
}
```

## 결과

요청 수 18,000여 회 → 37회. 수집은 정상적으로 끝났고 1만 건 넘게 받았다.

## 확정하지 못한 것

**클라이언트 빌드에 따라 갈리는 이유가 정확히 무엇인지는 확정하지 못했다.**
TLS 핸드셰이크 지문일 수도, HTTP/2 협상 차이일 수도 있다. 한때 "TLS 지문 기반 차단"이라고 단정했지만 그건 근거 없는 추측이었다.

확정된 사실은 두 가지뿐이다.

- 같은 URL·같은 헤더에서 **클라이언트 빌드만 달라져도 결과가 갈린다**
- 애초에 요청 수가 과했고, 그게 가장 큰 원인이었다

## 배운 것

**가설은 말로 세우지 말고 변수를 하나씩 고정해서 비교한다.**
"봇 차단인 것 같다"는 말로는 아무것도 좁혀지지 않는다. UA만 바꿔 두 번 호출한 것이 가설 하나를 확실히 지웠다.

**완전히 실패하는 것보다 부분적으로 성공하는 쪽이 좋은 단서다.**
전부 429였다면 원인을 좁히지 못했을 것이다. "A는 되는데 B는 안 된다"가 범위를 잘라 준다.

**429는 상대를 의심하기 전에 내 요청 수를 먼저 본다.**
우회할 방법을 찾는 데 시간을 쓰기 전에, 1만 8천 번 두드려야 하는 설계인지부터 따졌어야 했다.

**같은 이름의 실행 파일이 여러 개일 수 있다.**
Windows에서 `curl` 은 한 개가 아니다. 외부 프로세스에 의존하는 코드라면 "어느 바이너리가 잡혔는지"를 로그에 남겨 두는 편이 낫다.
