굿즈 도감 API에 캐시를 두 번 걸었다. 두 번 다 틀렸는데, 틀린 방식이 서로 달랐다.

한 번은 **쿼리가 무시돼** 모든 방문자가 같은 응답을 받았고,
한 번은 **캐시가 있는 자리가 비용이 드는 자리가 아니라서** 아무 효과가 없었다.

그 과정에서 정리된 개념들을 적어 둔다.

## 1. 캐시는 층을 이룬다

응답 하나를 만드는 비용은 한 군데 모여 있지 않다.

```
브라우저 ── 네트워크 ── 엣지 ── 네트워크 ── 함수 ── 네트워크 ── DB
```

캐시는 **"이 지점부터 아래는 건너뛴다"**는 선언이다.
그래서 어느 층에 두느냐가 무엇을 건너뛰는지를 정한다.

| 캐시가 있는 곳 | 건너뛰는 것 | 누가 공유하나 |
| --- | --- | --- |
| 브라우저 | 네트워크 전부 | 그 사람만 |
| 엣지(CDN) | 함수 호출, DB 조회 | 그 리전의 모든 방문자 |
| 함수 프로세스 | DB 조회 | 그 프로세스를 거친 요청만 |

**핵심은 어느 층이 비싼 구간 위에 있는지다.**

우리 쪽 비용을 재 봤다. 목록 전량을 받아 오는 데 이만큼 든다.

```
11,555행 / 12번 왕복 / 8.0초
왕복별   2668, 858, 608, 669, 740, 452, 332, 378, 349, 325, 301, 324ms
```

PostgREST가 한 번에 1000행까지만 주므로 왕복이 12번이다. 첫 왕복만 2.7초(연결 수립),
나머지는 300~900ms다.

함수 프로세스 안에 메모리 캐시를 두고 있었다. 그런데 콜드 요청은 계속 16초였다.
비용이 DB 구간에 있는 건 맞지만, **그 캐시가 프로세스 수명을 따라가기 때문**이었다.
(6번에서 다시 본다)

## 2. 캐시 키 — 무엇을 "같은 응답"으로 볼 것인가

캐시는 결국 사전이다. 키를 무엇으로 삼느냐가 성격을 결정한다.

키가 **너무 거칠면** 서로 다른 요청이 같은 칸을 쓴다. A가 요청한 응답을 B가 받는다.
이건 성능 문제가 아니라 **정확성 문제**다.

키가 **너무 세밀하면** 같은 응답인데 칸이 갈라져 캐시가 거의 안 맞는다.
요청마다 다른 키를 만들면 캐시가 없는 것과 같다.

HTTP 캐시에서 키의 기본 재료는 **메서드 + URL**이고, URL에는 쿼리스트링이 들어간다.
요청 헤더를 키에 넣고 싶으면 `Vary`로 밝힌다.

우리가 당한 쪽은 "너무 거친" 쪽이었다. 캐시를 걸고 나서 이렇게 됐다.

```
?character=A&limit=1   md5 5f917fc3…
?character=B&limit=1   md5 5f917fc3…   ← 같은 응답
?counts=1              items 11,555    ← 건수만 받아야 하는데 전량
```

화면에서는 이렇게 보였다. 특정 캐릭터 도감이 배경으로 전체 목록을 받아 **다른 캐릭터
굿즈가 섞이고**, `offset`이 무시돼 앞 120건이 두 번 들어가 총계가 틀렸다.

**캐시 키가 깨지면 증상이 "느리다"로 오지 않는다. "데이터가 틀리다"로 온다.**

## 3. 같은 플랫폼에 캐시 길이 여럿이다

여기가 이번에 제일 크게 배운 부분이다.

당시 나는 원인을 이렇게 적어 뒀다.

> 엣지 캐시가 경로만으로 키를 만들어, 쿼리가 달라도 처음 캐시된 응답 하나가 모두에게 돌아갔다

**이 진단이 틀렸다.** 엣지 캐시의 성질이 그런 게 아니었다.

플랫폼이 제공하는 캐시는 하나가 아니다. 최소 두 길이 있고, 설정이 비슷하게 생겼어도
성질이 다르다.

**(가) 응답 헤더로 거는 평범한 HTTP 캐시**

응답에 `s-maxage`를 붙이면 그 응답이 URL 기준으로 저장된다.
"요청이 오면 함수를 부르고, 그 결과를 보관한다"는 모양이다.
캐시 키 문서에는 이렇게 적혀 있다.

> The request URL (query strings are ignored for static files)

**쿼리를 무시하는 건 정적 파일뿐이다.** 함수 응답은 URL 전체가 키다.

**(나) prerender / ISR**

페이지를 미리 만들어 두고 주기적으로 다시 만드는 모양이다.
원래 "경로 하나에 문서 하나"를 전제로 설계됐기 때문에, **쿼리를 어떻게 다룰지가 별도
설정**으로 떨어져 있다. `allowQuery`가 그것이고, 정의가 이렇다.

> List of query string parameter names that will be cached independently.
> If an empty array, query values are not considered for caching.

빈 배열이면 **쿼리 값을 캐시에 고려하지 않는다.**

그리고 프레임워크의 라우트 규칙에 적은 한 줄이 둘 중 어느 길로 내려가는지는
프레임워크가 정한다.

```js
// 이것은 (나) 로 내려간다 — 쿼리가 키에서 빠진다
routeRules: { '/api/dex': { swr: 300 } }
```

```js
// 이것은 (가) 다 — URL 전체가 키다
setResponseHeader(event, 'cache-control', 'public, s-maxage=300, stale-while-revalidate=600');
```

**"캐시를 걸었다"는 말만으로는 어떤 키 규칙이 적용됐는지 알 수 없다.**
증상으로는 구별할 수 있다. 쿼리를 바꿨는데 같은 응답이 오면 키에 쿼리가 없는 길을 탄 것이다.

## 4. 신선도 — 세 개의 서로 다른 시간

`Cache-Control`에 적는 시간들은 서로 다른 대상에게 말을 건다.

```
max-age=N                     브라우저에게: N초 동안 묻지 말고 써라
s-maxage=N                    공유 캐시에게: N초 동안 신선하다고 봐라
stale-while-revalidate=N      만료 뒤 N초 동안: 묵은 걸 주고 뒤에서 갱신해라
```

`max-age`와 `s-maxage`를 나누는 이유는 **브라우저와 공유 캐시의 입장이 다르기** 때문이다.
공유 캐시는 금방 비울 수 있고 모두가 혜택을 본다. 브라우저 캐시는 그 사람 기기에 남아서,
길게 잡으면 "새로고침해도 안 바뀌는" 상태를 만든다.

그래서 흔한 모양이 `max-age=0, s-maxage=300`이다.
**브라우저는 매번 물어보지만 그 물음이 엣지에서 끝난다.**

플랫폼이 이걸 대신 해 주기도 한다. Vercel 문서에 이런 문장이 있다.

> If only `Cache-Control` is used, Vercel strips the `s-maxage` directive from the header
> before it's sent to the client.

즉 `public, s-maxage=300`만 보내도 브라우저가 받는 글자는 `public, max-age=0, must-revalidate`다.
캐시는 엣지에만 생긴다.

`stale-while-revalidate`는 **만료 순간의 비용을 누가 치를지**에 대한 답이다.
이게 없으면 만료 직후 도착한 한 명이 전액을 기다린다. 있으면 그 사람도 묵은 값을 즉시
받고 갱신은 배경에서 돈다. 대신 그 사람은 조금 오래된 값을 본다.
그 교환이 받아들여지는지가 판단 기준이다.

## 5. HIT · MISS · STALE

캐시를 거친 응답은 셋 중 하나다. 같은 사이트에서 세 종류를 뽑아 봤다.

### 정적 자산 — 교과서적인 캐시

```
Cache-Control: public, max-age=31536000, immutable
X-Vercel-Cache: HIT
Age: 109004
```

1년 캐시, `immutable`. 파일명에 내용 해시가 박혀 있어서 **내용이 바뀌면 이름이 바뀐다.**
그러니 영원히 캐시해도 안전하다. `Age: 109004`는 이 응답이 엣지에 30시간째 앉아 있다는 뜻이다.

### 페이지 — ISR

```
Cache-Control: public, max-age=0, must-revalidate
X-Vercel-Cache: STALE
Age: 75040
```

5분 ISR을 걸어 뒀는데 `Age`가 **20.8시간**이다.
`stale-while-revalidate`가 일하고 있다는 신호다. 만료됐지만 **그동안 아무도 들어오지
않아서 갱신이 돌 기회가 없었다.** 묵은 복사본을 즉시 주고, 배경에서 새로 만든다.

`STALE`은 고장이 아니다. 다만 `Age`가 만료 시간의 몇십 배라면 트래픽이 없다는 뜻이기도 하다.

### API — 캐시 없음

```
Cache-Control: public, max-age=0, must-revalidate
X-Vercel-Cache: MISS
Age: 0
```

`s-maxage`가 없다. 엣지는 저장하지 않고, 영원히 `MISS`다.
매번 함수가 깨어나 DB를 12번 왕복한다.

`MISS`가 계속 뜨면 둘 중 하나다. 저장하라고 말하지 않았거나, **키가 매번 달라서 같은 칸을
두 번 쓰지 못하거나.** 두 번째는 "캐시를 걸었다"고 믿고 있을 때 생기므로 더 찾기 어렵다.

### 측정 함정 하나

`curl -I`로 헤더를 보려 했는데, 한참 엉뚱한 값을 보고 있었다.

```
curl -sI /api/dex?...     →  404 Page not found
                             cache-control: no-cache
```

`-I`는 **HEAD** 요청을 보낸다. 핸들러를 GET 전용으로 등록해 두면 HEAD는 라우트에 걸리지
않고 404로 떨어진다. 그 404의 헤더를 읽고 있었던 것이다.

```
curl -s -o /dev/null -D - /api/dex?...   →  200 OK
```

**헤더를 볼 때도 실제 메서드로 쳐야 한다.**

## 6. 지역 캐시와 공유 캐시

같은 "캐시"라는 말이 전혀 다른 두 가지를 가리킨다.

**지역 캐시**는 프로세스 메모리 안에 있다. 빠르고 공짜지만 **프로세스 수명을 따른다.**
서버리스에서는 이 성질이 특히 중요하다. 인스턴스가 트래픽에 따라 뜨고 죽으므로,
지역 캐시는 "언제든 비어 있을 수 있는 캐시"다.

1번에서 "메모리 캐시가 있는데 콜드 요청이 16초"였던 게 이것이다.
비용은 DB 구간에 있고 캐시도 그 위에 있었지만, **새 인스턴스에는 그 캐시가 없다.**

그리고 인스턴스가 여럿이면 **서로 다른 내용을 들고 있을 수 있다.**
여기서 나온 사고가 하나 있었다. DB 읽기가 한 번 실패해 **빈 목록**이 지역 캐시에 들어갔고,
그 인스턴스만 계속 "데이터가 없습니다" 화면을 냈다. 다른 인스턴스는 정상이라 재현이 안 됐다.

그래서 지역 캐시에는 규칙이 하나 더 필요했다. **빈 결과를 성공으로 캐시하지 않는 것.**
일시적 실패를 캐시하면 그 실패가 만료될 때까지 반복되고, 빈 결과를 캐시하면
"데이터가 없는 화면"이 정상으로 굳는다.

**공유 캐시**는 프로세스 밖에 있다. 인스턴스가 바뀌어도 남고, 모두가 같은 값을 본다.

"캐시를 넣었는데 콜드 요청이 여전히 느리다"는 증상은 대개
**공유 캐시가 필요한 자리에 지역 캐시를 둔 것**이다.

## 7. 무엇을 공개 캐시에 둘 수 있는가

공유 캐시의 응답은 **그 뒤에 오는 모두에게 그대로 나간다.**
그래서 캐시 가능성은 성능 문제이기 전에 **데이터 경계 문제**다.

기준은 "이 응답이 요청한 사람에 따라 달라지는가"다. 달라지면 공개 캐시에 둘 수 없다.
키에 사용자를 넣는 방법도 있지만, 그러면 적중률이 사용자 수에 반비례해 떨어져
캐시를 두는 의미가 대개 사라진다.

이 경계가 설계를 밀어내는 방향이 있다. **개인 자료를 응답에서 빼면 그 응답은 캐시할 수
있게 된다.** 로그인 상태 표시를 서버 렌더에서 빼고 브라우저에서 그리게 하면,
페이지 HTML이 누구에게나 같아져 공유 캐시에 올릴 수 있다.

> 이 경계를 실제로 밟았던 이야기는 따로 적어 뒀다 —
> [ISR을 켜기 전에 걸린 두 가지]({{ site.baseurl }}{% post_url 2026-11-23-isr-cache-and-payload %})

즉 **"캐시할 수 있는 응답"과 "캐시할 수 없는 응답"을 섞지 않도록 쪼개는 것**이
캐시 설계의 큰 부분이다.

## 8. 캐시가 못 고치는 것

CDN의 원래 목적은 캐시가 아니라 **거리**였다. 가까운 노드가 응답하면 왕복 시간이 줄어든다.

그런데 캐시가 맞지 않으면 요청은 원본까지 간다. 그러면 **엣지가 가까운 것은 도움이 되지
않고, 원본이 어디 있는지가 전부를 결정한다.**

여기서 구별할 게 있다.

- **정적 자산**은 내용이 고정이라 모든 노드에 퍼뜨려도 안전하다 → 전 세계 캐시
- **함수 응답**은 언제든 바뀔 수 있어서 보통 **요청이 들어온 리전에만** 캐시된다

그리고 Vercel의 `X-Vercel-Id`를 읽으면 원본이 어디서 도는지 보인다.

```
icn1::iad1::xxxxx-…
 │      └─ 함수가 실제로 돈 리전 (버지니아)
 └──────── 요청을 받은 엣지 (서울)
```

리전을 따로 지정하지 않았더니 기본값으로 돌고 있었다.
**서울에서 들어온 요청이 태평양을 건너가서 DB를 12번 왕복한다.**

캐시를 걸어도 남는 비용이 셋이다.

1. **첫 번째 요청은 언제나 전액**이다. 캐시가 비는 순간은 없앨 수 없다
2. **왕복 횟수**는 캐시가 줄여 주지 않는다. 한 번에 받을 수 있는 행 수의 상한 때문에
   N번 왕복해야 한다면, 캐시가 비었을 때는 매번 N번이다
3. **거리**도 캐시가 줄여 주지 않는다. 원본과 DB가 멀면 `MISS`마다 그 거리를 치른다

**캐시는 비싼 일을 덜 자주 하게 만드는 도구다. 비싼 일을 싸게 만들지는 않는다.**
그 둘을 섞으면 캐시를 걸어 두고 원인을 안 들여다보게 된다.

## 정리

- 캐시는 층을 이루고, **어느 층이 비싼 구간 위에 있는지**가 효과를 정한다
- 키가 거칠면 **정확성**이 깨지고, 세밀하면 적중률이 사라진다.
  캐시 키가 깨진 증상은 "느리다"가 아니라 "데이터가 틀리다"로 온다
- 같은 플랫폼에 캐시 길이 여럿이고 **길마다 키 규칙이 다르다**.
  "캐시를 걸었다"는 말로는 어느 길인지 알 수 없다
- `max-age`는 브라우저, `s-maxage`는 공유 캐시,
  `stale-while-revalidate`는 **만료 순간의 비용을 누가 치를지**
- 지역 캐시는 프로세스 수명을 따르고, 인스턴스별로 다른 값을 들 수 있다.
  **빈 결과와 실패는 캐시하지 않는다**
- 캐시 가능성은 성능이 아니라 **데이터 경계**의 문제다
- 캐시는 비싼 일을 **덜 자주** 하게 하지만 **싸게** 만들지는 않는다

두 번 틀린 게 서로 다른 층의 문제였다는 걸 뒤늦게 알았다.
한 번은 키(3번), 한 번은 층(6번)이었다. 둘 다 "캐시를 걸었다"로 뭉쳐서 생각하고 있었기
때문에 같은 실수로 보이지 않았다.
